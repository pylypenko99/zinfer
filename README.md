# zinfer

Інференс LLM на CPU, написаний на Zig з нуля, без залежностей (навіть libc). Читає GGUF, підтримує архітектури Llama 2/3, Mistral, Qwen2 і Qwen3.

## Збірка

Потрібен Zig **0.17.1**.

```sh
zig build                  # ReleaseFast, -mcpu=native (AVX2/FMA/F16C підхоплюються автоматично)
zig build test             # тести кернелів, репаку, attention і токенізатора
zig build -Dcpu=baseline   # портабельний бінарник (повільніший)
```

## Запуск

```sh
zig-out/bin/zinfer -m model.gguf -p "The capital of France is" -n 64 --temp 0
zig-out/bin/zinfer -m model.gguf --chat -s "You are a helpful assistant."
zig-out/bin/zinfer -m model.gguf -p "..." --draft 3     # спекулятивне декодування через n-gram lookup
zig-out/bin/zinfer -m model.gguf --server              # запуск HTTP сервера (порт 8080) для автовиявлення в omp (llama.cpp)
zig-out/bin/zinfer -m model.gguf --port 8080          # вказати порт (сумісно з OpenAI /v1/chat/completions та /v1/responses)
zig-out/bin/zinfer -m model.gguf --no-prune            # вимкнути двофазний vocab pruning на lm_head
zig-out/bin/zinfer -m model.gguf --bench 256,64        # pp256 + tg64, як у llama-bench

`zinfer -h` показує всі опції (семплінг: `--temp`, `--top-k`, `--top-p`, `--min-p`, `--seed`; ресурси: `-t`, `-c`, `-b`).

## Підтримка

| | |
|---|---|
| Архітектури | `llama` (Llama 2/3.x, Mistral, TinyLlama), `qwen2`, `qwen3`, `lfm3` (Liquid LFM-3: 13 short-conv + 11 GQA шарів, sandwich norms, sigmoid gate, SWA) |
| Типи ваг | Q4_0, Q8_0, Q4_K, Q5_K, Q6_K: швидкі x8-кернели; F16, BF16, F32: построкові |
| Токенізатори | byte-level BPE (`gpt2`: Llama 3, Qwen, LFM2/3), SentencePiece BPE (`llama`) |
| Чат-шаблони | Llama 3, ChatML, LFM (автовизначення за спецтокенами, опція `--no-think`), інакше plain |
| RoPE | normal/NeoX, `rope_freqs` (Llama 3.1+), окремий SWA RoPE base (LFM3), лінійне масштабування |

## Швидкість

i7-8550U (4 ядра / 8 потоків, AVX2), DDR4 з піком читання ~28 GB/s, 4 потоки. Порівняння з llama.cpp b12019 у режимі лише CPU (`-ngl 0 -dev none`). Обидва бінарники запускалися по черзі в однакових умовах, токени/с:

| Модель | zinfer pp256 | llama.cpp pp256 | zinfer tg64 (base) | zinfer tg64 (pruned) | llama.cpp tg64 |
|---|---:|---:|---:|---:|---:|
| Llama-3.2-1B Q4_K_M | 194 | 154 | 32.3 | **38.5** (+31%) | 27.0 |
| Qwen3-0.6B Q8_0 | 243 | 130 | 39.2 | **48.1** (+23%) | 31.5 |
| Qwen3-0.6B Q4_0 | 308 | 184 | 61.3 | **68.4** (+12%) | 50.6 |
| Qwen3-0.6B Q5_K_M | 246 | 214 | 49.8 | **55.2** (+11%) | 42.6 |
| LFM-3-Coder-1.7B Q4_K_M | 128 | 107 | 23.4 | **27.8** (+19%) | 18.4 |
Генерація впирається в пропускну здатність пам'яті: для Llama-1B це ~25 GB/s, тобто ~88% виміряного піку.

Коректність перевірено так: жадібний (`--temp 0`) вивід збігається з llama.cpp токен у токен на Llama-3.2-1B (Q4_K_M), TinyLlama-1.1B (Q4_0, SentencePiece), Qwen3-0.6B (Q4_0, Q5_K_M, F16) і LFM-3-Coder-1.7B (Q4_K_M, 812 токенів промпта з SWA). Токенізація складних рядків (кирилиця, CJK, емодзі, пробіли й переноси, код) теж збігається з llama.cpp для Llama 3, Qwen, TinyLlama та LFM3. Логіти точно не збігатимуться: квантування активацій у 8 біт розривне, тож уже збурення ваг на 1e-6 зсуває їх на ~0.5.

## Звідки швидкість

- **Репак ваг при завантаженні** (`src/repack.zig`). Кожні 8 рядків матриці переставляються так, що один 32-байтний вектор містить по 4 ваги з 8 рядків. 4 байти активації розмножуються на всі лейни, і `vpmaddubsw` рахує часткові суми одразу для 8 вихідних рядків: лейни вектора і є рядками. Горизонтальних редукцій немає, масштаби застосовуються до 8 рядків однією інструкцією, а Q4 накопичує 8 груп в i16 до розширення. Біти квантизації не змінюються.
- **Активації квантуються в 8 біт** один раз на матмул (Q8_K / Q8_0 зі зсунутими на 32 байти `qs`), тож внутрішній цикл цілочисельний.
- **Один шлях для prompt і генерації**: forward приймає батч токенів, і кожен блок ваг читається з RAM один раз на батч (до 4 токенів на розпакований блок).
- **Software prefetch** на 4 KiB уперед: апаратні префетчери зупиняються на межі 4K-сторінки. Дає +12% до генерації.
- **Huge pages**: ваги лежать в анонімній пам'яті з `MADV_HUGEPAGE`.
- **Attention у стилі flash**: K зберігається транспонованим тайлами по 16 позицій (f16), кожен тайл конвертується один раз на 4 запити (GQA-голови та токени промпта), softmax онлайн. На pp1024 це 176 ток/с проти 128 у llama.cpp.
- **Dynamic Two-Stage Vocab Pruning на `lm_head`** (`--no-prune` для A/B перевірки): вихідна матриця важить ~215 МБ (128k словник), читання якої забирало понад 26% часу генерації. При завантаженні 25% вимірів матриці пакуються в неперервний буфер (40–54 МБ). Під час генерації швидкий грубий GEMM та min-heap за 2.0 мс відбирають топ-512 динамічних груп + 64 базові групи найчастіших токенів, після чого повний GEMM обчислюється лише для них (~0.4 мс). Зменшує час обчислення логітів у 3.2x і прискорює генерацію Llama-1B з 32.3 до **38.5 ток/с** зі 100% збереженням точності argmax.
- **Prompt Lookup Decoding** (`--draft N`, n-gram спекуляція): пошук 2/3-грамних збігів у контексті та пакетна верифікація кандидатів за один прохід читання ваг. На задачах із повторенням синтаксису (код, JSON, таблиці) піднімає генерацію з 32 до 50–140 ток/с (до **3.4x прискорення**).
- **Пул потоків**: потоки крутяться в спіні між диспетчами, тож на проході немає syscall; QKV і gate/up злиті в один диспетч, рядки роздаються динамічно.
- Обходи для LLVM: інтрінсики AVX2 через `extern fn @"llvm.x86..."` (компілятор сам згортає завантаження), `vmovd+vcvtph2ps` для fp16, щоб не було хибної залежності через акумулятор, і невидимі для оптимізатора межі циклів, щоб LLVM не розгортав їх із спілами.

## Обмеження

- Тільки dense-трансформери перелічених архітектур, без MoE і без vision.
- Немає YaRN/NTK rope scaling, тож довгі контексти поза тренувальним вікном деградують.
- Пре-токенізатор написаний вручну: ASCII точний, класи Unicode наближені таблицями.
- F16/BF16/F32-ваги йдуть повільним построковим шляхом (prefill не оптимізовано).
- x86 з AVX2 — основна ціль. На інших CPU працює портабельний `@Vector`-код без спецоптимізацій (NEON/AVX-512 VNNI не налаштовано).

## Дорожня карта подальших оптимізацій (Roadmap)

1. **Квантування KV-кешу (Q8_0 або Q4_0 для K і V)** — *прискорення на контекстах від 4k*. Зменшення об'єму кешу в RAM у 2–4 рази (на 32k контексті не 704 МБ, а 176–352 МБ) та прискорення вичитки кешу ядрами уваги.
2. **Злиття операцій (Fused RMSNorm + Quantization)** — *+5–8% до prefill*. Об'єднання знаходження суми квадратів $\sum x^2$ зі збереженням одразу в масштабований і квантований `i8` без проміжного запису та повторного читання `f32` у кеш L1/L2.
3. **Tree-based Speculative Decoding** — перевірка не одного лінійного ланцюжка n-грамів, а невеликого дерева (2–3 найімовірніші гілки). Оскільки пакетний прохід перевіряє кандидатів за той самий час, що й один токен, acceptance rate зростає з 40–50% до 70–85%.
4. **Draft Model Speculative Decoding** — запуск легкої моделі-чернетки (наприклад, Qwen-0.6B Q4_0 на 60–140 ток/с) поруч із великою цільовою моделлю (Llama-3-8B або LFM3-1.7B) для генерації довгих текстів без повторюваних n-грамів.
5. **Системне профілювання Linux** — перемикання CPU governor у режим `performance` та оптимізація охолодження/лімітів TDP ноутбука (+15–20% стабільної частоти при тривалому навантаженні).
