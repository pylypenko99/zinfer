# zinfer

Інференс LLM на CPU, написаний на Zig з нуля, без залежностей (навіть libc). Читає GGUF, підтримує архітектури Llama 2/3, Mistral, Qwen2 і Qwen3.

## Збірка

Потрібен Zig **0.15.2**.

```sh
zig build                  # ReleaseFast, -mcpu=native (AVX2/FMA/F16C підхоплюються автоматично)
zig build test             # тести кернелів, репаку, attention і токенізатора
zig build -Dcpu=baseline   # портабельний бінарник (повільніший)
```

## Запуск

```sh
zig-out/bin/zinfer -m model.gguf -p "The capital of France is" -n 64 --temp 0
zig-out/bin/zinfer -m model.gguf --chat -s "You are a helpful assistant."
zig-out/bin/zinfer -m model.gguf --bench 256,64      # pp256 + tg64, як у llama-bench
```

`zinfer -h` показує всі опції (семплінг: `--temp`, `--top-k`, `--top-p`, `--min-p`, `--seed`; ресурси: `-t`, `-c`, `-b`).

## Підтримка

| | |
|---|---|
| Архітектури | `llama` (Llama 2/3.x, Mistral, TinyLlama), `qwen2`, `qwen3` |
| Типи ваг | Q4_0, Q8_0, Q4_K, Q5_K, Q6_K: швидкі x8-кернели; F16, BF16, F32: построкові |
| Токенізатори | byte-level BPE (`gpt2`: Llama 3, Qwen), SentencePiece BPE (`llama`) |
| Чат-шаблони | Llama 3 і ChatML (визначаються за спецтокенами), інакше plain |
| RoPE | normal/NeoX, `rope_freqs` (Llama 3.1+), лінійне масштабування |

## Швидкість

i7-8550U (4 ядра / 8 потоків, AVX2), DDR4 з піком читання ~28 GB/s, 4 потоки. Порівняння з llama.cpp b12019 у режимі лише CPU (`-ngl 0 -dev none`). Обидва бінарники запускалися по черзі в однакових умовах, токени/с:

| Модель | zinfer pp256 | llama.cpp pp256 | zinfer tg64 | llama.cpp tg64 |
|---|---:|---:|---:|---:|
| Llama-3.2-1B Q4_K_M | 194 | 154 | 32.3 | 27.0 |
| Qwen3-0.6B Q8_0 | 243 | 130 | 39.2 | 31.5 |
| Qwen3-0.6B Q4_0 | 308 | 184 | 61.3 | 50.6 |
| Qwen3-0.6B Q5_K_M | 246 | 214 | 49.8 | 42.6 |

Генерація впирається в пропускну здатність пам'яті: для Llama-1B це ~25 GB/s, тобто ~88% виміряного піку.

Коректність перевірено так: жадібний (`--temp 0`) вивід збігається з llama.cpp токен у токен на Llama-3.2-1B (Q4_K_M), TinyLlama-1.1B (Q4_0, SentencePiece) і Qwen3-0.6B (Q4_0, Q5_K_M, F16). Токенізація складних рядків (кирилиця, CJK, емодзі, пробіли й переноси, код) теж збігається з llama.cpp для Llama 3, Qwen і TinyLlama. Логіти точно не збігатимуться: квантування активацій у 8 біт розривне, тож уже збурення ваг на 1e-6 зсуває їх на ~0.5.

## Звідки швидкість

- **Репак ваг при завантаженні** (`src/repack.zig`). Кожні 8 рядків матриці переставляються так, що один 32-байтний вектор містить по 4 ваги з 8 рядків. 4 байти активації розмножуються на всі лейни, і `vpmaddubsw` рахує часткові суми одразу для 8 вихідних рядків: лейни вектора і є рядками. Горизонтальних редукцій немає, масштаби застосовуються до 8 рядків однією інструкцією, а Q4 накопичує 8 груп в i16 до розширення. Біти квантизації не змінюються.
- **Активації квантуються в 8 біт** один раз на матмул (Q8_K / Q8_0 зі зсунутими на 32 байти `qs`), тож внутрішній цикл цілочисельний.
- **Один шлях для prompt і генерації**: forward приймає батч токенів, і кожен блок ваг читається з RAM один раз на батч (до 4 токенів на розпакований блок).
- **Software prefetch** на 4 KiB уперед: апаратні префетчери зупиняються на межі 4K-сторінки. Дає +12% до генерації.
- **Huge pages**: ваги лежать в анонімній пам'яті з `MADV_HUGEPAGE`.
- **Attention у стилі flash**: K зберігається транспонованим тайлами по 16 позицій (f16), кожен тайл конвертується один раз на 4 запити (GQA-голови та токени промпта), softmax онлайн. На pp1024 це 176 ток/с проти 128 у llama.cpp.
- **Пул потоків**: потоки крутяться в спіні між диспетчами, тож на проході немає syscall; QKV і gate/up злиті в один диспетч, рядки роздаються динамічно.
- Обходи для LLVM: інтрінсики AVX2 через `extern fn @"llvm.x86..."` (компілятор сам згортає завантаження), `vmovd+vcvtph2ps` для fp16, щоб не було хибної залежності через акумулятор, і невидимі для оптимізатора межі циклів, щоб LLVM не розгортав їх із спілами.

## Обмеження

- Тільки dense-трансформери перелічених архітектур, без MoE і без vision.
- Немає YaRN/NTK rope scaling, тож довгі контексти поза тренувальним вікном деградують.
- Пре-токенізатор написаний вручну: ASCII точний, класи Unicode наближені таблицями.
- F16/BF16/F32-ваги йдуть повільним построковим шляхом (prefill не оптимізовано).
- x86 з AVX2 — основна ціль. На інших CPU працює портабельний `@Vector`-код без спецоптимізацій (NEON/AVX-512 VNNI не налаштовано).
